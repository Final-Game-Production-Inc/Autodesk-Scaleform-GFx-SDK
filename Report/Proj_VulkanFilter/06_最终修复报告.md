## 1. 概要

本轮把 Vulkan 后端滤镜路径上**四个相互叠加的缺陷**全部修掉。它们表面上是"点按钮就卡死/崩溃"、"顺利通过四个字不见了"，本质集中在三类问题上：

1. **引用所有权**：临时渲染目标的 depth/stencil 引用被裸指针接住后丢失，导致它永远留在 `RBCL_InUse`，`RenderBufferManager::EndFrame()` 断言。
2. **资源销毁顺序**：Vulkan 的 framebuffer 引用 image view，而 view 属于可回收的 buffer/texture；三处释放路径都早于 framebuffer 的实际销毁，校验层把命令缓冲判为 invalid，驱动侧 `0xC0000005`。
3. **渲染状态记账**：嵌套渲染目标弹出后没有重开父级 render pass，后续遮罩/合成绘制落在 pass 外被驱动丢弃 —— 这就是"四个大字没了"。

修复后行为与 D3D11 参考一致，滤镜不再需要环境变量开启。

## 3. 根因分析

### R1 临时 RT 的 DS 引用泄漏（P1）

`Vulkan::HAL::CreateTempRenderTarget()` 用**裸指针**接 `CreateDepthStencilBuffer()` 的返回值；D3D11 的同一函数用 `Ptr<DepthStencilBuffer>`（`D3D1x_HAL.cpp:745`）。该返回值自带一个引用，Vulkan 侧从不释放：

- 复用池命中（`RS_Match`）时，这张 DS 永远停在 `RBCL_InUse`；
- 第一次出现"带遮罩的滤镜/混合目标"的那一帧，`RenderBufferManager::EndFrame()` 的 `"render targets still 'in-use'"` 断言必炸。

**取证**：自建迷你调试循环抓断点地址 `0x140276B834`，用 PDB publics 反查落在 `RBGenericImpl::RenderBufferManager::EndFrame (+0xCC)`；在 `EndFrame` 加临时探针后打印 `inuse=1 type=5`（`RBuffer_DepthStencil`）。

### R2 DS 视图早于 framebuffer 销毁（P3 第一层）

`PopRenderTarget()` 摘掉 DS 后立即归还池子，而引用该 view 的 framebuffer 只是**入队**延迟删除（`RenderTargetData::PendingDeletes`）。同一帧 `EndFrame` 的池回收就会销毁 view，校验层随即报：

```
VkImageView ... was destroyed, which was used by VkFramebuffer ...
commandBuffer is now in an invalid state (instead of recording state)
```

### R3 `UpdateData()` 换下 DS 时当场释放（P3 第二层，真正的"最后一击"）

同一个临时 RT 被复用成"不需要 stencil"的 pass 时，`CreateTempRenderTarget()` 的 `else` 分支执行 `UpdateData(..., 0, ...)`，直接把 `pDepthStencilBuffer` 置空 —— 被换下的 DS 引用归零 → `delete` → `~DepthStencilSurface()` 里 `vkDestroyImageView()` **立即**执行。而上一张带 stencil 的 framebuffer 还在延迟队列里。

**取证**：加 `[DSCREATE] / [RETIRE] / [DSVIEW-DESTROY]` 探针后，日志出现 `[DSCREATE] rt=4AF8A1F0 ds=4AF8A2D0 view=0xD9A7`，随后该 RT 的 `[RETIRE] ds=0`（弹出的 DS 已为空），紧接着 `[DSVIEW-DESTROY] view=0xD9A7` —— 说明它在中途被 `UpdateData` 释放，而非退役流程。

### R4 framebuffer 按 slot 延迟、RT/DS 退役"每帧全清"（P3 第三层）

`PendingDeletes` 分 3 个 frame slot，`DrainPendingDeletes()` 只清当前 slot；退役队列却每帧清空。于是 slot 1 的 framebuffer 还没轮到，它引用的 view 就被释放了。

### R5 嵌套临时 RT 未重开 pass（P4）

"渐变矩形 + 文字遮罩"（`EXract\shapes\41.svg` + 文字图形）会形成"滤镜 RT 里再套一层 RT"。子 pass 的 `PopRenderTarget()` **结束**了 render pass，但代码只在栈回到 1（主目标）时重开 pass；回到 2（父级临时 RT）时 `InRenderPass=false`，后续遮罩/合成绘制全部落在 pass 外。

**取证**：在 `drawPrimitive()` 加探针，打印 `[NOPASS] draw(6) stack=2 main=1 hs=0xBF` 共 **631 次**；校验层对应 10 条 `VUID-vkCmdDraw-renderpass`。驱动丢弃这些 draw，字形遮罩因此为空。

### R6 负视口高度不合规（P2）

HAL 用负 `VkViewport.height` 做 Y 翻转（对齐 D3D/GL），但 `Platform_Vulkan.cpp` 把 `VkApplicationInfo::apiVersion` 写死为 **1.0**。规范 VUID-VkViewport-apiVersion-07917 要求：除非启用 `VK_KHR_maintenance1` 或 `VK_AMD_negative_viewport_height`，负高度只在 **Vulkan ≥ 1.1** 合法。

## 4. 修复方案

| # | 问题 | 修法 | 位置 |
|---|---|---|---|
| F1 | R1 | DS 统一用 `Ptr<DepthStencilBuffer>` 接管（与 D3D11 一致）；`CreateRenderTarget(Texture*)` 同样处理 | `Vulkan_HAL.cpp:982`、`:933` |
| F2 | R2/R3/R4 | `UpdateData()` 换下/清空的 DS 存入 `PendingDSDeletes[slot]`；`DrainFrameResources()` 按 **framebuffer → DS → target(texture)** 顺序释放，且先 `DrainAllPendingDeletes()` 清掉所有 slot 的 framebuffer（此时队列已 idle） | `Vulkan_HAL.h:432-445`、`Vulkan_HAL.cpp:407` |
| F3 | R2 | 临时 RT 整体退役记录 `{ Ptr<RenderTarget>, Ptr<DepthStencilBuffer> }`，`PopRenderTarget()` 入队，drain 时统一释放 | `Vulkan_HAL.h:352`、`Vulkan_HAL.cpp:1441` |
| F4 | R2 | `RenderBufferManager` 增加 `AllowsDeferredBufferRelease`（Vulkan 置 true），`EndFrame` 对"确定性延迟一帧"的缓冲放行；`SetInUse` 对已 evict（`RTS_Lost`）节点直接忽略 | `Render_Buffer.h:255`、`Render_BufferGeneric.cpp:130`、`:508` |
| F5 | R5 | 新增 resume 版离屏 render pass（`LOAD_OP_LOAD`；初始布局 `SHADER_READ_ONLY` / `DEPTH_STENCIL_ATTACHMENT`；子依赖与 CLEAR 版逐字段一致，满足 00904 兼容性）；`PopRenderTarget()` 在栈 >1 时用它重开父级 pass | `Vulkan_HAL.cpp:1819`、`:1388` |
| F6 | R6 | 查询 `vkEnumerateInstanceVersion` 后声明 1.1（加载器不支持则回退 1.0） | `Platform_Vulkan.cpp:195-202` |
| F7 | 收口 | 滤镜默认开启，`GFX_VK_NOFILTERS=1` 回退 | `Vulkan_HAL.cpp:1571` |

### 4.1 资源退役顺序（核心不变式）

```
DrainFrameResources()            // 平台已 wait 该 slot 的 fence
  ├─ DrainPendingDeletes()       // 当前 slot 的 framebuffer
  ├─ DrainAllPendingDeletes()    // 其余 slot 的 framebuffer（队列已 idle）
  ├─ DrainAllPendingDSDeletes()  // 被换下的 depth/stencil buffer
  └─ PendingTargetReleases       // fb → DS → target(texture)
```

只要保持 **framebuffer 永远先于它引用的 image view 销毁**，`was destroyed, used by VkFramebuffer` 这一类错误就不可能再出现。

### 4.2 resume pass 的兼容性要点

render pass 兼容性（VUID-VkRenderPassBeginInfo-renderPass-00904）**包含子依赖的 stage/access**。因此 resume 版与 CLEAR 版必须：

- 附件格式、采样数、附件引用布局一致；
- `VkSubpassDependency` 的 `src/dstStageMask`、`src/dstAccessMask` 完全一致；
- 只允许 `loadOp` 与 `initialLayout` 不同。

同一 framebuffer 可直接用于两者，无需第二套 framebuffer 缓存。

## 8. 经验与后续建议

**经验**

1. Vulkan 里"buffer 释放"≠"view 销毁"≠"framebuffer 销毁"，三者必须显式排序；任何一处提前都会让整条命令缓冲失效（而不是只丢一个 draw）。
2. 有延迟删除的后端不能沿用"帧末清空"的记账假设；引擎的 `EndFrame` 断言需要为这类后端留一个**显式、有界**的放行口，而不是关掉断言。
3. render pass 兼容性包含子依赖；做 resume/变形 pass 时依赖字段必须逐字段照抄。
4. 交叉验证 D3D11 同类实现（`CreateTempRenderTarget` 的 `Ptr` 用法）能最快暴露所有权差异。

**建议后续**

1. 用 `Release`/`Shipping` 构建补一轮回归（本轮只验证 `Vulkan_Debug_Static`）。
2. 关掉校验层跑长时 soak（30~60min × 多样本），观察内存曲线（退役队列是否有滞留）。
3. 若后续要开滤镜缓存（`GFX_VK_FILTER_CACHE`），需按同一套"fb → view → buffer"顺序复核缓存结果的回收。
4. 把 `repro_click.ps1` 接进 CI（或本地 pre-commit），以"校验层 0 报错 + 关窗 exit=0"为门禁。
